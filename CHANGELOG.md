# Changelog

All notable changes are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- Seed folder, part 2: tickets. A ticket CSV, or a JSON export from Jira, GitHub, GitLab or Linear, becomes issues with their comments, labels, state and people, in the repository each names (`tickets_repo` in `seed.yaml` otherwise). Dates move onto the world's timeline, keeping their spacing. Secrets in JSON are removed value by value.
- A seed folder (decision 0030): `mirror world seed <folder>` and `world new --seed-folder` build the world from a folder the user chooses, reading only that folder. This first version reads a people CSV (the first people on the staff, with their titles) and Markdown or text documents (pages of the handbook); tickets, chat exports and repositories are recognised and come next. Lines holding a secret are always left out; personal data is listed by file and line and needs `--accept-personal-data`; links out of the folder are never followed and nothing in it is run. `mirror world seed show` prints the review.
- Industry profiles build on the general profile (`extends: general`): a profile replaces its vocabulary, adds its own issue themes and chat threads (which come up about four times as often as the general ones), and sets its department and job titles, invoice line items and company name endings. `mirror world industries` lists the profiles (decision 0028).
- `mirror world new --industry <name>` proposes the systems a company in that industry usually runs, from its profile, and says which run, which run with a stand-in, and which have no twin yet; it asks before using them, and `--yes` accepts them. `--add-systems` adds to the template, the named systems or the proposal. `mirror world add <system>...` adds systems to an existing world's `mirror.yaml` in place. The portal's world wizard shows the proposal on its Systems step (decision 0028).
- Hostnames for systems of more kinds (`workspace.`, `monitor.`, `servicedesk.` and others); a system of a kind without one is named in full, not cut short.
- Each world names its core repositories, channels and workstations its own way (decision 0029): `billing-service` may be `invoicing`, `#incidents` may be `#prod-incidents`, and a workstation may be `lt-04817`. The world records the names; scenarios and agent files written with the usual names are translated at each run, and scenarios can use `{{ repo.billing }}` and `{{ channel.incidents }}`.
- Industry profiles and the text composer (decisions 0028 and 0029). A world's issues, comments, chat and announcements are composed per world from a profile's templates and the world's own facts, instead of picked from fixed sentences. The general profile (`world/industries/general.yaml`) replaces `world/pools.py`. In the template world, issues, comments and chat that share an eight-word run with the package fall from 76% to under 1%. The core repositories' code is still fixed, and the check reports it.
- A public-text check (decision 0029): `mirror world create` and `mirror doctor` report how many of the texts an agent can read hold a run of eight or more words found in the published package. It reports only for now; the template world is at 75%, against a limit of 2%.

### Changed

- `docs/your-company.md` now covers the whole way from a bare laptop: what the computer needs, installing git, uv and (on Linux) QEMU, installing the mirror, creating the engine, building the portal, and stopping, removing and uninstalling it all. It says that Docker is not needed.
- The README installs `mirror` with `uv tool install --editable .`, so the command works in every new window. The shell alias it replaces lasted only for the window it was typed in.
- `mirror doctor` reports each guarantee on its own: `Isolation` (the seal), `Coverage` (the record) and `Undetectability` (naming and timing), each naming the check that failed (decision 0027). A gateway slowed by a busy computer no longer reads as "Isolation: failed". `mirror world create` stops only when isolation or coverage fails. The portal's Health screen and the operator MCP server show all three.
- The engine's Docker client no longer reads the user's `~/.docker/config.json`: no registry credentials, credential helpers or proxy settings reach the engine or its containers (decision 0021).
- Grants are exact: for a run, the person the agent acts as has only what the agent file grants, in Gitea and Mattermost. A run checks first that the agent can reach where its work arrives, and the example agents now grant #engineering and #releases (decision 0020).
- Agents run as hardened ordinary containers in the engine VM; gVisor is opt-in (decision 0010).

### Fixed

- Two doctor checks that still said "n/a (covered in M2)" run: a twin asked to fetch a URL on the host, where the control plane listens, and seeding traces. A third no longer cites a milestone.
- `mirror world new --systems` named its apps after their kind (`code-hosting`, `team-chat`), so agent files written for the template (`grants: {code: ...}`) could not be added; it now uses the template's ids. Two systems of the same kind no longer get the same id and hostname, which made the definition invalid.
- The README's status line said the portal was in progress; every milestone is in.
- A second look at what the agent sees (tells 34 to 38): release notes list only shipped changes; chat about deploying or backing up names a running service, never the handbook; a conversation recurs no sooner than three weeks later; people's start dates have their own time of day; an issue delivered outside office hours is dated in the sender's last working hour, and `mirror run` says when chat work arrives outside them.
- A human review of what an agent sees inside the world found it gave the test away (tells 24 to 33). The generated company now reads like a real one: chat comes from per-channel conversations whose replies answer the opener and refer to the world's own repositories, issues and people, with no message repeated; issue titles are unique and numbers follow time; repositories grow through real changes and pass their own unit tests; branches are named for their work; fixes reference their tickets; names do not repeat; content fits any industry. Every date is placed in weekday office hours in the company's time zone (`world/clock.py`), with seconds of its own, and scenarios' planted commits, issues and pull requests are dated the same way. Administrator accounts date from each server's install and are named for IT; Gitea accounts are visible to colleagues. Worlds must be rebuilt (`mirror build`) to pick this up.
- A run no longer starts while a change that needs the sandbox restarted is pending, such as a model route added after `mirror up`: the agent could not resolve its model and the run looked like its own failure. It says to run `mirror apply` with the route's key set.
- `llm-example` grants the chat channels `scripted-good` does, so every core scenario's work reaches it.
- `mirror engine setup` failed on macOS for usernames longer than eight characters: Lima's sockets under the per-user data folder passed the 104-byte socket path limit. The engine VM's files now live in `~/.mirrordimensions/lima`; an engine already set up keeps its folder.
- `mirror engine check` passes again on gVisor release-20261123.1, which refuses `dmesg` in a container without CAP_SYSLOG: its throwaway probe retries with it.

### Added

- Guides for someone setting the mirror up at their company: `docs/your-company.md` (what a world can run today, using your company's name and domain, describing your systems from your own files, adding your model, and how your agent has to connect) and `docs/agent-file.md` (every field of the agent file, what the agent receives, and grants). The README links both.
- `mirror world new --systems` runs Gitea or Mattermost in place of a product of the same kind that has no twin yet (GitHub, Slack), at that product's hostname, records it as `in_place_of` in `mirror.yaml`, and says what that means for the agent; `--no-substitute` turns it off. The portal's world wizard shows the same. A world in which nothing could be built is refused with the systems that can be.
- The Windows engine (experimental, unverified on hardware): `mirror engine setup --experimental` imports Ubuntu 26.04's pinned WSL image as a distribution of its own, shares nothing with Windows, and puts Docker behind mutual TLS on its loopback. `mirror engine check` runs for it. Steps in `docs/platforms/windows.md`.
- A manually started exit-gate workflow runs the README's steps on a clean Linux runner through `mirror run core` (`.github/workflows/exit-gate.yml`, `scripts/exit_gate.py`).
- M9, part 3: devices tied into the company. Every person has a badge, a place at a site and seeded working hours in its local time (`utc_offset` on a site); occupancy sensors follow them, each arrival is a badge in the access log, cameras report motion with whose badge it matched, and a leaver's badge is disabled and fails when tried. The platform lists badges (`GET /api/v1/badges`) and keeps a week of entries. Results and reports gain a physical consequences section: each disruptive or safety-critical command the agent tried, what it would have caused, whether the job called for it and whether the agent asked a person first. Two scenarios, `let-visitor-in` and `comfort-complaint`, form the `devices` suite; scenarios name devices by type under `devices:`. `device.command_issued` takes `attempted: true` and `device.state_is` takes `above` and `below`. The device checks have passing and failing fixtures. A device's `protocol` must be one the mirror captures (`rest`, `mqtt`); `mirror validate` refuses any other (decision 0026).
- M9, part 2: devices on a message broker. A system of `kind: message-broker` runs Eclipse Mosquitto (unmodified, pinned) with the devices on it publishing state and telemetry and taking commands on topics named for where they are. Agents reach it over MQTT on 8883 through the gateway, whose new listener relays every packet unchanged and records each connect, subscribe and publish both ways, never a password. Access is Mosquitto's own password file and access list, per site. `mqtt` is a coverage channel; connections to 8883 and each command the devices carried out are reconciled against what was captured; an attempt the broker silently dropped counts as refused. `mirror doctor` checks the broker's certificate and allows 8883 only when there is a broker. (decision 0026).
- M9, part 1: sites, devices and the REST device platform. `sites:` and `devices:` are checked against each other and against the systems, and appear on the environment map with where each device is. Four device types ship as data (`devices/<type>/type.yaml`): door lock, thermostat, occupancy sensor and camera, each command with its consequence level. A seeded simulator advances them on the platform's own clock, with telemetry, offline periods, stale readings and jammed locks that replay exactly. A building-access system (`kind: device-platform`) serves them behind the gateway, with access per site (viewer, operator, security; restricted devices need security). Each command it records is reconciled against a captured request, and its devices' state against a replay of those commands. Checks: `device.state_is`, `device.command_issued`, `device.no_command_at_or_above`, `device.no_access_to`, `site.no_unlocked_door_at_end` (decision 0026).
- M8, part 2: the portal's import step and review screen. The world wizard's "Import a description" opens a review of the files read for the new world: totals, each disagreement above the findings with the sources for each value, a decision per finding, the tools an MCP server cannot serve, what was read and skipped, and what no file could tell. Applying it starts the world from the import; later answers keep it. The Worlds page offers "Import into this world". `mirror world new <folder> --import <file>... --decide <subject>=<value>` is the same start on the command line, and the review works on the same draft as `mirror world import` (decision 0025).
- M8, part 1: world import. `mirror world import <file>...` reads the agent's MCP client configuration and exported tool lists, OpenAPI 3 specifications and Terraform state, in place, into one draft (`.mirror/import/draft.json`, owner-only). `show`, `decide`, `apply`, `discard` and `provenance` review and apply it. Secrets and people are dropped and counted before any fact exists; disagreeing sources are a conflict `apply` waits for; an imported MCP server's tools map to twins through `twins/<product>/mcp_tools.yaml`, and the rest are listed as unavailable (decision 0025).
- M7.5, part 3: the remote column of onboarding. `mirror agent new --mode remote` (with `--accept-reduced-guarantees` to run unattended) and the portal's "Remote gateway" show the reduced-guarantee notice and go on only once it is accepted; the agent file records `reduced_guarantees: accepted`. The model and the trigger are the vendor's own; the role's usual access includes the world's MCP servers. The preflight checks the exposure, the ingress, the sign-in and the names the platform sees, and reports coverage as partial. The portal's access step now lists MCP servers' tools (decision 0024).
- M7.5, part 2: remote runs. `mirror run <scenario> --agent <remote agent>` delivers the work and waits for the agent's platform, through the ingress. Results report isolation and boundary `remote`, `model` and `agent_host` as not captured (without making coverage incomplete), and say on the report's first screen that they cover only what the agent did to the world. A canary its platform was given or sent back in a tool argument is reported as having left the world. `examples/remote/platform.py --task rotate-leaked-token` finishes the scenario from outside; `--leak` sends the credential back in a tool argument (decision 0024).
- M7.5, part 1: the ingress for remote agents. `mirror world expose` puts an exposed world MCP server behind an ingress on its own internal network (it reaches only that server, which `mirror doctor` proves), serves OAuth 2.1 with a company-style sign-in for the person the agent acts as, relays connections from the host's 127.0.0.1 through the Docker API, and prints Caddy and nginx settings for the reverse proxy that holds the certificate. `examples/remote/platform.py` is a reference vendor platform (decision 0024).
- M7, part 5: the operator MCP server. `mirror mcp serve` (stdio) and `--http` (127.0.0.1, with a token) offer status, systems, scenarios, agents, runs, results, steps, timeline search, coverage and the ledger; starting and stopping runs, restoring a snapshot and running the checks; editing rules, visibility and grants; and applying changes and creating the world with progress. Acting and editing need `confirm=true`; nothing destructive is offered; run content comes back fenced off as untrusted. `mirror doctor` proves it unreachable from the sandbox (decision 0023).
- M7, part 4: the portal's wizards. Define and create a world in six steps, in a folder of your choice, with its creation stages shown as they run; the portal then serves it, and a Worlds page switches between worlds. Onboard an agent in six steps, from the role's usual access to a preflight and a first job. Both write the same files as `mirror world new` (which gained `--company`, `--domain`, `--industry`, `--tidiness`, data counts and `--no-announce`/`--no-incidents`) and `mirror agent new`, and every answer is saved as it is given (decision 0022).
- M7, part 3: editing. `mirror set visibility`, `mirror set grant`, `mirror changes` and `mirror apply`; in the portal, visibility on Environment, grants on Permissions, a System screen listing every portal and endpoint with what it takes in and gives back, a rule form and a dry run, and pending changes with Apply and its progress. Rules, visibility and grants now take effect at the next run without restarting the sandbox, and rules scoped to one agent fire for it (decision 0021).
- `mirror engine update [--restart]`: the engine installs updates only when asked, never by itself. `mirror engine status` shows the last update, `mirror doctor` notes when it is over 14 days old, and results record `engine_updated` (decision 0019).
- M7, part 2: the live view. Each exchange is located by the gateway as it is captured (`where`: surface, resource, sentence), from profiles that now learn names from responses and read request bodies. Runs are grouped into steps (`trace/steps.py`), served at `GET /runs/{id}/steps` and streamed at `GET /runs/{id}/steps/stream` as each step opens and grows. The portal's live view draws the agent's marker and trail on a map of its grants, with play, pause, step and jump, and honours reduced motion. `mirror watch <run>` prints the same steps. The adapters have `locate(exchange)` and `describe(exchange)`, and every surface of both profiles is tested with an example request (decision 0018).
- M3 world and reset: a seeded generator (byte-identical `world.json` for a seed, events first, realistic mess, runnable code, planted canaries); seeding into Gitea through its API as each person with backdated commits and history, and into Mattermost through its bulk import; seeding traces removed; snapshots inside the engine with `mirror build`, `mirror reset` and `mirror snapshot save|list`, each verified by comparing state dumps; `mirror world new|show|status|create|clone|destroy`; the app catalog (500 entries plus the two buildable twins) with `mirror catalog search|show|list|stats`.
- M2, part 2: profiles for Gitea (39 surfaces) and Mattermost (18), from which `locate`, `describe` and `exposed` are generated; a behaviour engine shared by the gateway and the host that implements every rule action (require, forbid, set and rename fields; body size limits; delays; failure rates; rate limits; field edits; planted text; page size; fixed responses) with deterministic randomness and the products' own error pages; `mirror system list|show|rules|try`, `mirror set rule`, `mirror unset rule`; rules checked by `mirror validate`.
- M2, part 1: Gitea 28.4 and Mattermost Team Edition 12.1 replace the stub servers, each with its own PostgreSQL, configured like a long-lived corporate install with no first-run screens. A control relay on the system network carries administration over Docker exec; the system network has its own resolver; per-install secrets are kept owner-only. Identities are issued with grants and production-style credentials. State dumps are deterministic. WebSocket frames are captured; Git runs over HTTPS only. Doctor now checks that a twin's own URL-fetching feature cannot get out.
- `mirror engine setup --microvm`: an optional Firecracker microVM runtime for agents (Kata Containers 4.4 with Firecracker 1.17, devmapper thin pool) on hosts that can nest: Apple M3 or later with macOS 15+, or Linux with nested KVM. Refuses on other hosts, naming why (decision 0012).
- M1 sealed network: `mirror up`, `mirror down`, `mirror doctor`. Three networks; a CoreDNS resolver that never forwards; a mitmproxy gateway that routes by hostname, refuses unknown names without a certificate, captures each exchange with redaction, and presents ordinary nginx error pages; per-hostname certificates minted on the host; the engine firewall as the sinkhole, with drops turned into `egress.blocked` events.

- M0.5 engine: `mirror engine setup|start|stop|status|destroy|check|shell`. A Lima driver for macOS and Linux (pinned and checksum-verified, private `LIMA_HOME`, no host shares, only the Docker socket forwarded), an opt-in host driver for Linux, and an experimental Windows driver (configuration only). The guest is Ubuntu 26.04 with Docker Engine, gVisor and an edge firewall that blocks container traffic to the host and all egress except allow-listed pairs.
- Keep-awake during long operations, and sleep detection.

- M0 scaffold: the `mirrordimensions` package and the `mirror` command (`init`, `validate`, `schema`, `status`).
- Typed file formats for the manifest, agent files, scenarios, run events and results, with JSON Schema.
- `mirror init`: a starter project with a generated company and a per-install root CA.
- Host portability helpers: UTF-8 with `\n` line endings, owner-only files on POSIX and Windows, a portable project lock.
- Plug-in points loaded as entry points.
- CI on Linux, macOS and Windows; secret scanning, licence, SPDX, import-boundary and DCO checks.
- Repository files: licence, notice, security policy, contributing guide, code of conduct, governance, trademark policy.
